## TEST
An LLM-driven security analyst for Wazuh. You ask a question in plain language
("correlate the severity-12 events over the last 20 days", "is data being
exfiltrated from my endpoints?"), and a local model plans its own investigation choosing which Wazuh queries to run, reading the results, and iterating until it can give a verdict. Every query it runs is logged as an
audit trail.


## Architecture

Three files, one job each:

| File | Role |
|------|------|
| `app.py` | Web UI (Flask) + process control. The only file you run. |
| `agent_tools.py` | The agentic loop and the tools the model can call. |
| `client.py` | Data layer: Wazuh API + indexer access. No logic |

The model reaches Wazuh two ways: the **Wazuh indexer API** (`:9200`, basic auth) for alerts/aggregations/timelines, and the **Wazuh server API** (`:55000`, token auth) for
live host inventory.

## Requirements

- **Python 3.10+**
- **Ollama** running somewhere reachable, with a model pulled.
  Tool calling needs a capable model — Search at [Ollama](https://ollama.com/search)
  Small models (3B-4B) will not call tools reliably.
- A **Wazuh** deployment (manager + indexer) you can reach over the network.

## Setup

### 1. Install dependencies

```bash
pip install flask flask_cors ollama requests
```

### 2. Create a `.env` file

Place a `.env` in the same directory as `app.py`.

```ini
# -- Wazuh API (token auth, port 55000) --
WAZUH_HOST=https://<WAZUH_SERVER_IP>:55000
WAZUH_USER=your_api_user
WAZUH_PASS=your_api_password
WAZUH_SSL=false       # true only if you verify TLS certs

# -- Wazuh Indexer (basic auth, port 9200) --
INDEXER_HOST=https://<WAZUH_INDEXER_IP>:9200
INDEXER_USER=admin
INDEXER_PASS=your_indexer_password

# -- Ollama (the LLM backend) --
OLLAMA_HOST=http://127.0.0.1:11434   # where Ollama listens
OLLAMA_MODEL=qwen3      # the tool-calling model to use
OLLAMA_THINK=false      # see "Must-know: OLLAMA_THINK" below before enabling

# -- Optional tuning --
AGENTIC_MAX_STEPS=18            # max tool calls per investigation
UI_HOST=0.0.0.0                 # interface the web UI binds to
UI_PORT=5000                    # web UI port

# -- Optional: email delivery for reports (leave all blank to disable) --
SMTP_HOST=
SMTP_PORT=587
SMTP_USER=
SMTP_PASS=
SMTP_FROM=
SMTP_TO=
```

Notes:

- `WAZUH_PASS` and `INDEXER_PASS` are **required** — the app fails fast at
  startup if either is unset rather than silently falling back to Wazuh's
  known-weak quick-start credentials (`wazuh`/`wazuh`, `admin`/`admin`).
- If Ollama runs on a different machine (e.g. a GPU host), make sure it listens on the network (`OLLAMA_HOST=0.0.0.0:11434` on that host) and the port is open.
- Email delivery is entirely optional. If `SMTP_HOST`/`SMTP_TO` are blank, the
  "email" checkbox/button in the UI will just report a config error instead
  of sending anything — nothing else is affected.


## Running

`app.py` has built-in process control - no `nohup`, no PID hunting.

```bash
python3 app.py start      # launch in the background (writes agent.pid + agent.log)
python3 app.py status     # is it running? on which port?
python3 app.py stop       # stop the background process cleanly
python3 app.py restart    # stop + start
python3 app.py run        # run in the FOREGROUND (Ctrl+C to quit; use for systemd)
```

Both spellings work: `python3 app.py stop` and `python3 app.py --stop`.

Then open the UI:

```
http://<host>:5000
```

### Using it

- **Run tab** - type a question, click **Run now**, confirm, and watch the
  agent investigate live (its tool calls, reasoning, and final verdict stream
  in over SSE). Check **Email report on completion** to have the result
  emailed when it finishes (requires SMTP config, see above). Click **Stop**
  to cancel a running investigation.
- **Reports tab** - every completed investigation is saved with its verdict and
  full tool-call audit trail. Reports render as formatted markdown, plus a
  structured view (executive summary, severity, affected hosts, key findings,
  recommendations, IOCs) generated by a second LLM pass.
- **Context tab** - a free-text "Environment Notes" box that gets injected
  into *every* investigation's system prompt verbatim, as durable background
  the model can't otherwise infer from raw alerts — e.g. "10.0.11.15 is our
  Greenbone vulnerability scanner, treat its traffic as authorized" or
  "tonybet.com is our corporate domain." This is the main lever for tuning
  day-to-day behavior without touching code. See the caution below before
  writing incident-specific notes here.
- **Auto-run** - toggle the scheduler to fire a triage automatically every
  `interval_hours` hours, looking back over the last `hours` hours of events,
  with its own "auto-email the result" checkbox independent of the manual
  Run tab's.

### Must-know / gotchas

- **Only one investigation runs at a time.** The Run tab and a scheduled
  auto-run share the same lock. If you fire a manual run while the scheduler
  is due (or vice versa), one of them just gets "an investigation is already
  running" and does nothing — it is not queued.
- **`OLLAMA_THINK=true` is expensive.** Only enable it for small/fast models
  (e.g. `qwen3:8b`). On a 14B+ model, thinking mode has been observed to push
  a single investigation to 9+ hours. Leave it `false` unless you've
  benchmarked your specific model.
- **Keep Context-tab notes to durable environment facts, not incident
  details.** The notes text is injected unconditionally into every run's
  system prompt, including scheduled runs days or weeks later. A note like
  "watch out for the Shellshock alert we saw on host X at 07:24 on the 1st"
  can cause the model to re-surface that specific old finding in a much
  later run's report as if it were newly discovered in the current window.
  Stick to facts that stay true indefinitely (scanner IPs, domain names,
  which integrations are expected) rather than references to a specific
  past event.
- **`search_alerts`'s `query=` is a literal substring match, not semantic
  and not a field filter.** If a report says "no matches for X" or "search
  returned zero despite the aggregate count," that usually means the wording
  guess didn't appear verbatim in the alert text — not that the activity is
  absent. The agent is instructed to prefer `aggregate_alerts` /
  `search_alerts(rule_group=...)` over guessing free text, but if you see a
  report second-guessing itself over a text-search mismatch, that's why.
- **Local state lives in three gitignored JSON files** next to `app.py`:
  `investigations.json` (report history, capped at the last 50 runs),
  `sched_cfg.json` (scheduler settings), `context_cfg.json` (the Context-tab
  notes). None of this is committed or backed up automatically — copy them
  yourself if you reinstall or move the deployment and want to keep history.
- **A `"status": "completed"` report isn't necessarily a real triage.** If a
  tool call fails in an unexpected way, the model can end up producing a
  short non-answer (e.g. asking a question instead of a verdict) that still
  gets saved with `status: completed`. If a scheduled report reads as
  unusually thin or ends with a question, treat it as a failed run and
  re-check manually rather than assuming a quiet day.

## Areas for improvement

If you want to extend this, good directions:

- **More tools.** A `get_alert_detail` (pull one full event with every field),
  a `compare_time_windows` (this week vs. baseline), or an active-response hook
  (isolate a host) would extend what the agent can do.
- **Model selection in the UI.** Let the analyst pick the model per run instead
  of editing `.env`.
- **Surface the audit trail as a collapsible panel** in the live view, rather
  than only appending it to the saved report.
- **Persisted, searchable history.** History is currently a JSON file capped at
  50 runs; a small database would scale better and allow search.
- **Tighter convergence / cost control.** Larger models explore widely; a
  per-run tool-call budget surfaced in the UI, or a "quick vs. thorough" mode,
  would give users control over time/cost.
- **Multi-node / multi-tenant Wazuh.** The data layer assumes one manager and
  one indexer; supporting clusters would broaden its reach.
